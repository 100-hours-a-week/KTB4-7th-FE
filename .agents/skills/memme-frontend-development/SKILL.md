# 맴매 프론트엔드 개발 절차

공식 요구사항과 API 정의서는 참고가 아니라 구현 범위의 승인 기준이다. 화면·API·인증·V2/V3 범위를 추측해 채우지 않는다.

## 개발 시작 절차

1. 개발 전 기존 GitHub Issue를 확인한다. 없으면 한글 제목, 작업 범위, 완료 기준을 포함한 Issue를 먼저 만든다.
2. Issue가 준비된 뒤 요구사항 분석 → API 정의서 → 디자인·기획 문서 → 기존 코드 순서로 최신 내용을 확인한다.
3. 영향받는 화면, API, 인증, 오류·로딩·빈 상태, 접근성·보안 규칙을 식별한다. 누락·충돌·V2/V3 항목이면 사용자 승인 전까지 멈춘다.
4. 최신 `dev`에서 `feat/이슈번호-기능명` 브랜치를 만들고, 하나의 작은 기능 목적만 작업한다.
5. 페이지는 조합을, 기능은 사용자 흐름을, `shared`는 재사용 요소를 담당하게 한다. API 호출은 화면 컴포넌트에 중복하지 않는다.
6. 정상 흐름과 주요 오류·빈 상태의 테스트를 작성하고 실행한다.
7. 관련 테스트, 린트, 전체 빌드를 실행한다. 실패하면 원인을 해결하며 검증을 약화하거나 우회하지 않는다.

## PR 생성 절차

사용자가 “PR 올려줘”라고 요청한 경우에만 다음 절차를 사용한다.

1. 개발 시작 전에 만든 GitHub Issue가 연결돼 있는지 확인한다. PR 생성 시점에 새 Issue를 만들지 않는다.
2. 현재 브랜치가 해당 Issue의 `feat/이슈번호-기능명` 형식인지, 대상이 `dev`인지 확인한다.
3. `git status`와 diff를 확인해 하나의 작은 기능 단위인지, 관련 없는 파일이 없는지 검토한다.
4. 공식 요구사항·API 정의서 위반 여부와 API 변경 여부를 확인한다.
5. 새·수정 테스트, 관련 기존 테스트, 린트, 빌드를 실제 실행하고 결과를 확인한다.
6. 한글 커밋 메시지와 한글 PR 제목·본문을 준비한다. 본문에는 주요 변경사항, 구현 기능, 테스트 내용·결과, API 변경 여부, `Closes #이슈번호`를 포함한다.
7. commit·push·PR 생성 직전에 Issue, 생성 예정 브랜치, 커밋, PR 내용을 간단히 보여 주고 최종 승인 1회를 받는다.
8. 승인되면 추가 확인 없이 commit → push → `dev` 대상 PR 생성을 진행하고, Issue·브랜치·커밋·PR 제목·대상·테스트·빌드·링크를 보고한다.

## 환경·보안·CI 규칙

- API 주소는 `VITE_API_BASE_URL`로 관리한다. `.env`는 로컬 전용이며 Git에 넣지 않는다. `.env.example`에는 실제 비밀값 대신 필요한 변수 이름과 안전한 예시만 둔다.
- `feat/* → dev` PR의 CI는 린트, 테스트, 빌드를 실행한다. 실패를 우회하지 않는다.
- 운영 배포는 별도 승인된 호스팅·배포 절차가 마련되기 전에는 구성하거나 실행하지 않는다.

## 즉시 중단 신호

- “API 형식이나 인증 방식은 뻔하다.”
- “호환되니까 API를 미리 추가하자.”
- “V2/V3 내용을 먼저 구현해도 된다.”
- “편하니까 실제 비밀값을 추적 파일에 넣자.”
- “테스트를 건너뛰고 PR부터 만들자.”

위 상황은 공식 근거·검증·승인이 부족하다는 뜻이다. 먼저 보완한다.
